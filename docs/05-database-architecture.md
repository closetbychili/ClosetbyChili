# Closet by Chilli — Database Architecture

## 1. Purpose

This document defines the database architecture for Closet by Chilli.

The database is a critical part of the production e-commerce platform because it stores and protects:

- Products.
- Product variants.
- Categories.
- Collections.
- Customers.
- Wholesale accounts.
- Inventory.
- Pricing.
- Promotions.
- Carts.
- Orders.
- Payments.
- Shipping.
- CMS content.
- Audit records.

The primary database is PostgreSQL hosted through Supabase.

Django ORM is the primary application-level data access layer.

---

# 2. Database Architecture

The intended architecture is:

```text
                    Next.js
                       |
                       v
                Django REST API
                       |
                       v
                  Django ORM
                       |
                       v
                 PostgreSQL
                    /                      /                 Supabase      Supabase
             Auth         Storage
```

Supabase provides managed PostgreSQL infrastructure and supporting services.

Django remains responsible for application business logic.

---

# 3. Database Source of Truth

The production data model must have one authoritative relational database:

```text
PostgreSQL
```

The application accesses it through Django ORM.

The database must enforce important integrity rules independently of the frontend.

---

# 4. Supabase MCP and Schema Management

Supabase MCP will be used as an AI-agent tool for database operations.

The workflow is:

```text
Requirement
    ↓
Database design
    ↓
AI Agent
    ↓
Supabase MCP
    ↓
PostgreSQL
    ↓
Verification
    ↓
Django model/migration alignment
```

Supabase MCP must not be treated as permission to create arbitrary undocumented tables.

Every intentional schema change must be reflected in the project's database/domain documentation.

---

# 5. Django ORM and Supabase MCP

The project must avoid having two competing schema authorities.

The intended ownership model is:

```text
Business model
      ↓
Django model definition
      ↓
Migration
      ↓
PostgreSQL
```

Supabase MCP can assist with:

- Inspecting schema.
- Creating database objects during agentic development.
- Verifying constraints.
- Inspecting indexes.
- Inspecting data.
- Performing controlled database operations.

However, the resulting database state must remain reproducible through the project's migration strategy.

---

# 6. Database Naming Conventions

Use clear, predictable names.

Recommended:

```text
snake_case
```

Examples:

```text
product_variants
inventory_movements
wholesale_applications
order_items
payment_attempts
```

Avoid ambiguous names.

Use singular model names in Django and conventional plural table names where generated by Django.

---

# 7. Primary Keys

Primary keys should use a robust identifier strategy.

The exact identifier type will be selected during schema implementation, but the project should favor identifiers that:

- Are safe to expose publicly.
- Avoid predictable sequential IDs where public enumeration could be problematic.
- Work efficiently with PostgreSQL.
- Are supported well by Django.

Public resource identifiers must not automatically expose sensitive internal sequencing.

---

# 8. Foreign Keys

Relationships should use database-enforced foreign keys.

Examples:

```text
Product
  └── ProductVariant

Order
  └── OrderItem

User
  └── Address

Cart
  └── CartItem
```

Foreign keys must define appropriate deletion behavior.

Do not use cascading deletion blindly for business-critical historical records.

---

# 9. Soft Delete Policy

Soft deletion should be used selectively.

Good candidates may include:

- Products.
- Categories.
- Collections.
- CMS content.

Historical transactional records such as:

- Orders.
- Payments.
- Inventory movements.

should generally not be physically deleted merely because they are no longer active.

The exact retention policy will be defined in the domain documentation.

---

# 10. Product Data Model

The catalog should distinguish:

```text
Product
   |
   └── Product Variant
           |
           ├── SKU
           ├── Price relationship
           ├── Inventory
           └── Media
```

A product represents the merchandise concept.

A variant represents the purchasable configuration.

---

# 11. Product Variants

Variants should support properties relevant to apparel, such as:

- Size.
- Color.
- SKU.
- Variant-specific media.
- Inventory.
- Availability.

Do not duplicate the entire product record for every size/color combination.

---

# 12. SKU

Every sellable variant must have a unique SKU.

SKU must be:

- Unique.
- Non-empty.
- Stable.
- Suitable for inventory operations.

SKU should not be silently changed after inventory or order history depends on it.

---

# 13. Categories

Categories should support the business taxonomy.

Initial categories include:

```text
Kurtis
Kurta Sets
Dresses
Anarkali Sets
Dupattas
Bottom Wear
```

Subcategories may be introduced where required.

Category relationships should support hierarchical navigation.

---

# 14. Collections

Collections are separate from categories.

Examples:

```text
New Arrivals
Bestsellers
Festive Collection
```

A product can belong to:

- A category.
- Multiple collections.

Category describes taxonomy.

Collection describes merchandising.

---

# 15. Product-to-Collection Relationships

The relationship should support:

- Ordering.
- Active/inactive state where required.
- Collection-specific merchandising.

Do not duplicate product records merely to place them into different collections.

---

# 16. Customers

The application customer record should be separate from authentication provider internals.

Conceptually:

```text
Supabase Identity
       |
       v
Application User
       |
       └── Customer Profile
```

The database should store commerce-relevant application data, not authentication secrets.

---

# 17. Addresses

Addresses should be modeled separately from users.

A customer may have multiple addresses.

Potential types:

```text
Billing
Shipping
```

An order should preserve the address information relevant to that historical transaction.

Do not rely solely on the customer's current address when displaying an old order.

---

# 18. Wholesale Data

Wholesale must share the same customer and product infrastructure.

Conceptually:

```text
User
 |
 └── Wholesale Profile
       |
       ├── Approval status
       ├── Business information
       └── Wholesale eligibility
```

Wholesale approval state must be explicit.

---

# 19. Pricing Data

Pricing must support the fact that the client operates as both:

- Retailer.
- Wholesaler.

The database should therefore support distinct pricing concepts rather than storing a single universal price.

Conceptually:

```text
Product Variant
      |
      ├── Retail Price
      └── Wholesale Price / Rules
```

The exact pricing model will be defined in `11-inventory-pricing.md`.

---

# 20. Money Fields

All monetary values must use precise database numeric types.

Use PostgreSQL:

```text
NUMERIC / DECIMAL
```

Never use floating-point database fields for:

- Product prices.
- Discounts.
- Taxes.
- Shipping charges.
- Payment amounts.
- Refund amounts.

---

# 21. Currency

Every monetary value should have a clearly defined currency strategy.

The initial implementation should avoid silently mixing currencies.

If the platform initially operates in one currency, this should still be explicitly documented.

Multi-currency support should not be added unless required.

---

# 22. Inventory Architecture

Inventory must be modeled separately from catalog information.

Conceptually:

```text
Product Variant
      |
      v
Inventory
      |
      ├── Available
      ├── Reserved
      └── Movements
```

Inventory should support auditable state changes.

---

# 23. Inventory Movements

Inventory movements provide a history of stock changes.

Examples:

```text
STOCK_RECEIVED
MANUAL_ADJUSTMENT
ORDER_RESERVED
RESERVATION_RELEASED
ORDER_FULFILLED
RETURN_RECEIVED
DAMAGED
```

The exact event taxonomy will be defined in the inventory document.

---

# 24. Inventory Reservations

Reservations are temporary claims on stock.

Example:

```text
Available Stock
      |
      v
Reservation
      |
      ├── Released
      └── Finalized
```

Reservation logic must be concurrency-safe.

Two customers must not be able to successfully purchase the same final unit merely because two requests arrived simultaneously.

---

# 25. Carts

The database should support:

- Guest carts where required.
- Authenticated customer carts.
- Cart items.
- Quantity.
- Variant selection.
- Cart timestamps.

Cart data is mutable.

Cart data must not be treated as the historical source of an order.

---

# 26. Cart Items

A cart item should reference a purchasable product variant.

The backend must recalculate:

- Price.
- Availability.
- Discounts.
- Totals.

when relevant.

The client cannot determine the authoritative order total.

---

# 27. Orders

An order is an immutable historical business record except for explicitly permitted state changes.

An order should capture:

- Customer.
- Order number.
- Status.
- Currency.
- Pricing totals.
- Shipping information.
- Billing information.
- Payment state.
- Fulfillment state.
- Timestamps.

---

# 28. Order Items

Order items must preserve historical purchase information.

At minimum, an order item should capture the relevant:

- Product/variant identity.
- SKU.
- Product name snapshot.
- Selected variant information.
- Unit price.
- Quantity.
- Discount allocation.
- Tax allocation where applicable.
- Final line amount.

This prevents future product edits from changing historical order presentation.

---

# 29. Order Snapshots

Historical data must not depend entirely on mutable catalog records.

For example:

```text
Current Product Name
        ≠
Historical Order Product Name
```

An order should retain appropriate snapshots.

The same principle applies to:

- Prices.
- SKU where necessary.
- Product/variant display information.
- Addresses.
- Applied discounts.

---

# 30. Order Status

Order status should be explicit and controlled.

Potential states may include:

```text
PENDING
CONFIRMED
PROCESSING
SHIPPED
DELIVERED
CANCELLED
RETURNED
REFUNDED
```

The final state machine will be defined in `12-orders-payments-shipping.md`.

Arbitrary status changes should not be permitted.

---

# 31. Payments

Payments should be modeled independently from orders.

Conceptually:

```text
Order
  |
  └── Payment Attempts
          |
          └── Provider Events
```

An order may have multiple payment attempts.

This is important for:

- Failed payments.
- Retries.
- Provider callbacks.
- Refunds.

---

# 32. Payment Attempts

A payment attempt should record information such as:

- Order.
- Provider.
- Provider reference.
- Amount.
- Currency.
- Status.
- Attempt timestamp.
- Relevant metadata.

Sensitive payment credentials must never be stored unless explicitly required and securely designed.

---

# 33. Payment Webhook Events

Webhook events should be recorded where necessary for idempotency and auditing.

Potential information:

```text
provider
event_id
event_type
received_at
processed_at
processing_status
```

Provider event IDs should support duplicate detection.

---

# 34. Refunds

Refund records should be separate from the original payment attempt where appropriate.

A refund should track:

- Payment.
- Amount.
- Currency.
- Provider reference.
- Status.
- Reason.
- Timestamps.

Refund processing must be idempotent.

---

# 35. Shipping

Shipping data should be separated from the order core where practical.

Conceptually:

```text
Order
  |
  └── Shipment
        |
        ├── Carrier
        ├── Tracking
        ├── Status
        └── Timestamps
```

The database should support future multiple shipments if business requirements require it.

---

# 36. Promotions

Promotions should not be stored as a single text discount field on an order.

The system should preserve enough information to explain:

```text
Why was this discount applied?
How much was discounted?
Which rule/coupon caused it?
```

The detailed promotion schema will be defined later.

---

# 37. Coupons

Coupons should support:

- Unique code.
- Active/inactive state.
- Validity period.
- Usage constraints.
- Eligibility rules.
- Discount behavior.

Coupon usage must be concurrency-safe where limits exist.

---

# 38. CMS Data

CMS data should be stored separately from transactional commerce data.

Examples:

```text
Homepage
Banner
Content Block
Collection Section
```

CMS content should not be tightly coupled to order tables.

---

# 39. Media Data

Media metadata should be stored in PostgreSQL.

Actual files should be stored in Supabase Storage.

Conceptually:

```text
PostgreSQL
   |
Media Record
   |
Storage Path / Object Reference
   |
Supabase Storage
```

The database should store useful metadata such as:

- File path.
- MIME type.
- Alt text.
- Ordering.
- Related entity.
- Active state.

---

# 40. Audit Data

Audit records should be append-oriented.

They may reference:

```text
Actor
Action
Resource
Timestamp
Metadata
```

Audit history should not be casually edited or deleted.

---

# 41. Database Constraints

Important constraints should be implemented at the database level.

Examples:

```text
Unique SKU
Unique order number
Unique coupon code
Positive quantity
Valid foreign key
Valid price range
```

Database constraints protect against bugs from:

- Frontend.
- Backend.
- Admin.
- Scripts.
- AI agents.

---

# 42. Indexing Strategy

Indexes should be created based on actual query patterns.

Likely indexed fields include:

- SKU.
- Slug.
- Product status.
- Category relationships.
- Collection relationships.
- Order number.
- Customer ID.
- Order status.
- Payment provider reference.
- Inventory variant ID.
- Coupon code.

Do not create indexes blindly on every column.

---

# 43. Composite Indexes

Composite indexes should be considered for common query combinations.

Examples:

```text
product + active
category + active
customer + created_at
order_status + created_at
variant + inventory_state
```

The exact indexes should be validated against real query plans.

---

# 44. Uniqueness

Use database uniqueness for values that must be globally unique.

Examples:

```text
SKU
slug where required
order number
payment provider event ID
coupon code
```

Application-level duplicate checking alone is insufficient because of race conditions.

---

# 45. Nullability

Do not make fields nullable simply because it is convenient.

Every nullable field should represent a meaningful business state.

For example:

```text
shipped_at
```

may legitimately be null before shipment.

But:

```text
product.name
```

should not be nullable if every product requires a name.

---

# 46. Enumerated States

For controlled state fields, use explicit choices/enums.

Examples:

```text
OrderStatus
PaymentStatus
ShipmentStatus
WholesaleStatus
InventoryMovementType
```

The state values should be documented and stable.

---

# 47. Timestamps

Business entities should generally have appropriate timestamps such as:

```text
created_at
updated_at
```

Additional timestamps should be added when they represent meaningful state transitions.

Examples:

```text
paid_at
shipped_at
delivered_at
cancelled_at
approved_at
```

---

# 48. Deletion Strategy

Transactional records should generally be retained.

For example:

```text
Order
Payment
Refund
Inventory Movement
Audit Event
```

should not be physically deleted merely because an administrative user no longer wants to see them.

Use archival/inactive states where appropriate.

---

# 49. Referential Integrity

Foreign keys must prevent invalid references.

For historical records, deletion behavior should protect business history.

For example:

Deleting a product should not automatically delete historical order items.

---

# 50. Migration Strategy

Database schema changes must be reproducible.

The intended process is:

```text
Modify Django Model
        ↓
Create Migration
        ↓
Review Migration
        ↓
Apply Migration
        ↓
Verify Database
        ↓
Run Tests
```

Migrations must be committed to Git.

---

# 51. Supabase MCP Migration Rule

If Supabase MCP is used to make a schema change, the agent must ensure that the resulting schema is represented in the project's migration strategy.

Do not create production-only schema changes that cannot be reproduced.

If a change is made directly through Supabase MCP for development, the equivalent Django migration must still be considered and validated before the change becomes part of the official architecture.

---

# 52. Database Reset/Rebuild Test

The project must periodically verify that the database can be reconstructed from scratch.

Conceptually:

```text
Empty PostgreSQL
      |
      v
Django migrations
      |
      v
Required seed/configuration
      |
      v
Working application database
```

This protects against undocumented manual changes.

---

# 53. Seed Data

Seed data should be separated from migrations when appropriate.

Potential seed data:

- Initial categories.
- Development products.
- Development collections.
- Test admin users where appropriate.

Production seed scripts must not insert fake customer/order data accidentally.

---

# 54. Production Data Safety

AI agents and developers must treat production database operations as high-risk.

Agents must not:

- Drop production tables.
- Delete production data.
- Reset production databases.
- Modify large datasets blindly.
- Run destructive SQL without explicit approval.

---

# 55. Row-Level Security

Supabase supports PostgreSQL Row-Level Security.

The project must deliberately decide which database access paths require RLS.

Because normal commerce operations go through Django, authorization must remain enforced in Django.

If any client-side Supabase access is introduced, RLS policies become mandatory for those tables/data paths.

Never assume that hiding a table from the frontend is a security boundary.

---

# 56. Direct Client Database Access

The frontend should not directly perform sensitive commerce operations against PostgreSQL.

Do not allow the browser to directly:

```text
Create orders
Modify inventory
Change prices
Approve wholesale customers
Mark payments successful
```

These operations must pass through Django.

---

# 57. Supabase Service Role

Supabase service-role credentials are highly privileged.

They must:

- Never be exposed to the browser.
- Never be committed to Git.
- Be stored only in secure server-side configuration.
- Be used only where necessary.

---

# 58. Database Transactions

Use database transactions for multi-step operations requiring atomicity.

Example:

```text
Create Order
    +
Create Order Items
    +
Reserve Inventory
    +
Create Payment Attempt
```

The transaction design must account for external provider operations separately.

---

# 59. Isolation of External Calls

Do not keep a database transaction open while waiting unnecessarily for:

```text
Payment API
Shipping API
Email API
```

A better pattern is:

```text
Prepare internal state
    ↓
External operation
    ↓
Verify result
    ↓
Short transactional state update
```

The exact workflow depends on the provider.

---

# 60. Concurrency and Inventory

Inventory is especially sensitive to race conditions.

Example:

```text
Customer A ──┐
             ├── Last unit ──> Database
Customer B ──┘
```

The database/service layer must ensure that only valid inventory claims succeed.

Do not rely on:

```text
Frontend says "1 left"
```

as an inventory guarantee.

---

# 61. Order History Integrity

Historical orders must remain understandable even after:

- Product changes.
- Price changes.
- Category changes.
- Product deletion/inactivation.
- Customer address changes.
- Promotion changes.

Historical snapshots and order-specific records are therefore essential.

---

# 62. Data Normalization

Use relational normalization for core transactional data.

Avoid unnecessary duplication.

However, controlled denormalization/snapshots are acceptable when required for:

- Historical accuracy.
- Performance.
- Reporting.
- External integration compatibility.

Every intentional denormalization should have a documented reason.

---

# 63. Reporting

Operational reporting should initially use PostgreSQL queries/views where sufficient.

Do not introduce a separate data warehouse during Phase 1 unless required.

If analytics requirements grow, a dedicated reporting architecture can be introduced later.

---

# 64. Database Performance Rules

Before optimizing:

1. Identify the slow operation.
2. Inspect the SQL/query plan.
3. Measure.
4. Optimize.
5. Re-test.

Do not add random indexes or caches based on assumptions.

---

# 65. Database Security

Database security must include:

- Strong credentials.
- Encrypted connections in production.
- Restricted network access where possible.
- Least-privilege access.
- Secret management.
- Backups.
- Monitoring.
- Controlled administrative access.

---

# 66. Backups

Production PostgreSQL data must have an appropriate backup strategy.

The final deployment documentation must define:

- Backup frequency.
- Retention.
- Recovery process.
- Recovery testing.
- Responsibility for backups.

A backup that has never been restored/tested should not be considered fully reliable.

---

# 67. Database Monitoring

Production monitoring should track:

- Connection usage.
- Query performance.
- Slow queries.
- Database size.
- Index behavior.
- Lock contention.
- Failed connections.
- Backup status.

---

# 68. Data Retention

Retention rules should be defined for:

- Orders.
- Payments.
- Audit logs.
- Notifications.
- Webhook events.
- Customer data.

The project should not delete data merely to simplify tables without understanding business/legal requirements.

---

# 69. Database Environment Separation

At minimum:

```text
Development Database
Testing Database
Staging Database
Production Database
```

These environments must be isolated.

Never point local development tools at production unintentionally.

---

# 70. Database Testing

Tests should verify:

- Constraints.
- Relationships.
- State transitions.
- Transactions.
- Inventory concurrency where practical.
- Pricing calculations.
- Order creation.
- Payment state transitions.

---

# 71. Database Documentation Requirements

Whenever a new table/entity is introduced, documentation should specify:

```text
Purpose
Fields
Relationships
Constraints
Indexes
Lifecycle
Ownership
Security considerations
```

This is particularly important for AI-agent development.

---

# 72. AI Agent Database Workflow

Before creating/modifying database tables, the agent must:

1. Read relevant documentation.
2. Identify the owning domain.
3. Identify relationships.
4. Identify constraints.
5. Identify indexes.
6. Identify lifecycle/state rules.
7. Verify whether an existing table already solves the requirement.
8. Use Supabase MCP only after the design is clear.
9. Verify the resulting schema.
10. Align Django models/migrations.
11. Run tests.

---

# 73. AI Agent Database Safety

The agent must never:

- Drop tables without explicit approval.
- Rename tables casually.
- Remove columns without impact analysis.
- Remove constraints because they cause development errors.
- Disable security policies to make a feature work.
- Create duplicate tables for an existing domain.
- Store secrets in database records unnecessarily.
- Modify production data during normal development.

---

# 74. Database Definition of Done

A database change is complete when:

- The domain purpose is clear.
- The schema is documented.
- Relationships are correct.
- Constraints are defined.
- Indexes are justified.
- Django models are aligned.
- Migrations are reproducible.
- Supabase schema is verified.
- Tests pass.
- Existing data compatibility is considered.
- Security implications are reviewed.

# 77. Final Database Architecture

The database layer is:

```text
                 Django Application
                         |
                     Django ORM
                         |
                  PostgreSQL
                         |
                Supabase Platform
                  /      |                       /       |                    Database   Auth    Storage
```

For the commerce system:

```text
Frontend
   ↓
Django API
   ↓
Domain Services
   ↓
PostgreSQL
```

For asynchronous work:

```text
Django
   ↓
Redis
   ↓
Celery
```

Supabase MCP is an agentic development/operations tool, not a replacement for domain architecture.
